# 업무 접수 프로세스 설계 v1 — 홈페이지 문의연동 + 미팅 결과 등록

> 작성일 2026-08-13 · 관련 문서: `docs/하이파이브_08_v1.md`(현황), `docs/하이파이브_고도화_검토안_v1.md`(PHP 전환 검토)
> 이 문서는 **프로세스/워크플로 설계**이며 코드/스키마 구현은 아니다. PHP 전환은 별도 후속 프로젝트이므로, 여기서는 기술 스택과 무관하게 "업무가 어떻게 접수되어 실행 단위(업무)로 이어지는가"만 확정한다. 향후 PHP로 만들 때 이 문서의 상태값·데이터 항목·역할 표를 그대로 테이블/화면 설계에 옮기면 된다.

---

## 1. 왜 필요한가

중소기업이 겪는 전형적 문제 두 가지를 겨냥한다:
- 홈페이지로 들어온 고객 문의가 담당자 개인 메일함/휴대폰에만 남고, 회사 차원의 업무로 전환되지 않아 누락되거나 지연된다.
- 미팅에서 결정된 사항이 회의록(또는 메모)에만 남고, 실제 실행할 업무로 등록되지 않아 "말만 하고 끝나는" 경우가 반복된다.

목표는 **접수 채널이 여러 개여도 결국 하나의 업무관리 파이프라인(업무/Task)으로 합류**시키는 것이다. 담당자 입장에서 "일은 결국 다 여기 하나에 모인다"는 신뢰가 프로세스 설계의 핵심 기준이다.

---

## 2. 공통 원칙

1. **동일한 4단계 골격**: 두 채널 모두 `1차 접수 → 검토/정제 → 업무 등록 → 실행`을 따른다. 유입 형태(웹폼 vs 회의록)만 다를 뿐 마지막엔 항상 기존 "업무(Task)" 개념으로 합류한다.
2. **접수 즉시 자동 업무화하지 않는다**: 반드시 사람이 검토하는 중간 단계를 둔다. 스팸/중복 문의, 미팅 중 잡담까지 업무로 만들어지는 걸 방지하기 위함이다. 대신 검토가 방치되지 않도록 **담당자 알림 + SLA(예: 접수 후 영업일 1일 이내 확인)**를 못박는다.
3. **원본은 항상 보관, 전환은 파생**: 문의/회의록은 별도 기록으로 남고, 업무로 전환되면 원본과 업무 사이에 참조 연결을 유지한다 — "이 업무가 어디서 왔는지" 항상 추적 가능해야 한다.

---

## 3. 채널 A — 홈페이지 문의 접수 → 업무 등록

```
[홈페이지 문의폼]
   │ 방문자가 이름 / 연락처 / 문의유형 / 문의내용 입력 후 제출 (비로그인, 공개)
   ▼
[문의 접수 — 상태: 신규]
   │ 담당자에게 즉시 알림 (이메일/카카오/슬랙 — 기존 외부연동 채널 재사용 가능)
   │ 문의자에게 "접수 확인" 자동 회신 발송
   ▼
[담당자 검토 — 상태: 검토중]  (ADMIN/LEADER, SLA: 접수 후 1영업일 이내 확인)
   │
   ├─ 유효한 요청 ──▶ "업무로 전환" 실행
   │                    · 문의내용이 업무 비고에 자동 채워짐
   │                    · 담당자 지정, 프로젝트 선택(또는 신규 프로젝트 생성)
   │                    · 문의 상태 → 전환완료 (연결된 업무 ID 기록)
   │
   └─ 스팸/중복/단순문의 ──▶ 문의 상태 → 종결 (종결 사유 기록)
   ▼
[업무 등록 이후]
   │ 기존 업무관리 파이프라인 그대로 진행 (배정 → 진행 → 완료)
   ▼
[업무 완료]
   │ (선택) 문의자에게 처리 결과 안내 발송
```

### 수집 항목
| 항목 | 필수 여부 | 비고 |
|---|---|---|
| 이름 | 필수 | |
| 연락처(이메일 또는 전화) | 필수 | 회신용 |
| 문의유형 | 필수 | 분류값 — 예: 견적문의/기술지원/제휴/기타 |
| 문의내용 | 필수 | 자유 텍스트 |
| 접수시각 | 자동 | 서버 기록 |
| 유입경로 | 자동 | 현재는 "홈페이지" 고정값, 추후 이메일 파싱/전화상담 등 다른 채널 추가 시 구분용 |

### 역할
| 단계 | 담당 |
|---|---|
| 문의 제출 | 외부 방문자(비로그인) |
| 검토/전환/종결 | ADMIN, LEADER |
| 전환 이후 업무 실행 | 배정된 담당자(WORKER 포함) |

### 스팸 방지
동일 IP 또는 동일 이메일이 짧은 시간 내 반복 제출하는 것을 제한한다(예: 1시간당 N건). 공개 폼인 이상 필수 방어선이다.

## 4. 채널 B — 미팅 결과 → 업무 등록

```
[미팅 예정/진행]
   │ (선택) 미팅 제목/일시/참석자 사전 등록
   ▼
[회의록 작성 — 상태: 작성중]
   │ 미팅 중 또는 직후, 결정사항·액션아이템을 구조화해 기록
   │ 액션아이템 단위: { 할일 내용, 담당예정자, 목표일(선택) }
   ▼
[액션아이템 검토 — 상태: 확정 대상 선택]
   │ 회의록 작성자(또는 참석자)가 액션아이템 목록에서
   │ 실제로 업무가 될 항목만 체크
   ▼
[업무 변환 실행]
   │ 체크된 항목별로 담당자/목표일 확정 → "선택 항목 업무로 등록"
   │ 액션아이템 1건당 업무 1건 생성
   │ 업무 비고에 "OO 미팅(YYYY-MM-DD) 액션아이템" 형태로 원본 링크 기록
   │ 해당 액션아이템 → 상태: 전환됨 (연결된 업무 ID 표시, 중복 등록 방지)
   ▼
[회의록 보관]
   │ 회의록 원문은 계속 보관 — 과거 결정 이력 조회용
```

### 수집 항목
| 항목 | 필수 여부 | 비고 |
|---|---|---|
| 미팅 제목 | 필수 | |
| 일시 | 필수 | |
| 참석자 | 선택 | 자유 텍스트 또는 팀원 선택 |
| 액션아이템 리스트 | 선택(0건도 허용) | 각 항목: 내용 / 담당예정자 / 목표일 |

### 역할
| 단계 | 담당 |
|---|---|
| 회의록 작성 | 프로젝트 소속 멤버(참석자) 누구나 |
| 액션아이템 → 업무 전환 | 프로젝트 소속 멤버(참석자) 누구나 — 과도한 승인 절차 없음 |
| 전환 이후 업무 실행 | 배정된 담당자 |

과도한 승인 단계를 두지 않는 이유: 미팅 참석자가 그 자리에서 바로 업무로 못박아야 실효성이 있다. 채널 A(외부 문의)와 달리 이미 조직 내부 인원이 다루는 내용이라 별도 검토 단계가 불필요하다.

### 일부 항목만 전환
회의에서 나온 모든 발언이 업무가 되는 것을 방지하기 위해, 액션아이템 중 실제로 실행이 필요한 것만 선택적으로 전환한다. 단순 논의/참고사항은 회의록에만 남기고 업무화하지 않아도 된다.

## 5. 두 채널이 공유하는 데이터 흐름

```
[문의(Inquiry)] ──전환──▶ [업무(Task)] ◀──전환── [회의 액션아이템(MeetingActionItem)]
   (원본 보관)                                    (원본 보관)
```

- 둘 다 "원본 기록은 남기고, 실행 단위만 업무로 파생"시키는 동일 패턴이다. 향후 다른 접수 채널(이메일 파싱, 전화 상담 기록, 카카오톡 상담봇 등)이 추가돼도 같은 패턴을 재사용할 수 있다.
- 업무 쪽에는 **출처 표시**(직접등록 / 문의전환 / 미팅전환)를 남겨, "어느 채널에서 업무가 가장 많이 들어오는지" 같은 통계에도 활용할 수 있게 한다.

---

## 6. 상태값 정의 (향후 구현 시 그대로 사용)

| 개체 | 상태값 | 전이 |
|---|---|---|
| 문의(Inquiry) | `NEW`(신규) → `IN_REVIEW`(검토중) → `CONVERTED`(전환완료) \| `CLOSED`(종결) | 검토중에서만 전환/종결 분기 |
| 회의 액션아이템(MeetingActionItem) | `OPEN`(미전환) → `CONVERTED`(업무전환됨) | 전환은 되돌릴 수 없음(중복 방지) |
| 업무(Task) | 기존 상태 체계 그대로 사용 | 신규 필드: `sourceType`(DIRECT/INQUIRY/MEETING), `sourceId`(원본 참조 ID) |

## 8. 향후 구현 시 참고

- 이 문서의 상태값(`Inquiry.status`, `MeetingActionItem.status`)과 수집 항목 표를 그대로 DB 테이블 설계에 옮기면 된다.
- `Task.sourceType`/`sourceId`처럼 "출처 추적" 필드는 이후 통계(문의 전환율, 미팅 실행률 등)에 바로 쓸 수 있어 처음부터 넣어두는 것을 권장.
- 알림(신규 문의 접수, 전환 완료 안내)은 `docs/하이파이브_08_v1.md` §4.7에 정리된 기존 외부연동(Slack/잔디/카카오 등) 발송 패턴을 그대로 재사용하는 설계로 잡아두면, PHP로 옮길 때도 "알림 발송 지점이 어디인지"를 그대로 참고할 수 있다.
- 이번 설계는 코드/스키마 변경을 포함하지 않는다 — PHP 전환 착수 시점에 이 문서를 1차 스펙으로 삼아 테이블/화면을 설계하면 된다.
