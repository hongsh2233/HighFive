# 에이전시 인프라 전략 v1 — "카페24 최저가"에 갇히지 않는 확장 경로

> 작성일 2026-08-13 · 관련 문서: `docs/하이파이브_고도화_검토안_v1.md`(§4~5, 제품 단위 호스팅 검토)
> 이전 문서들은 "하이파이브 이 솔루션 하나를 어디에 올릴까"를 다뤘다. 이 문서는 사용자가 **소규모 개발 에이전시를 창업**하는 것을 전제로, 하이파이브 + 에이전시 홈페이지 + 향후 고객사 프로젝트들까지 함께 감당할 **인프라 전략**을 다룬다. "카페24가 제일 저렴해서 고르면 나중에 발목 잡히는 건 아닐까"라는 우려에 대한 답이다.

---

## 1. 질문을 다시 세우기

"어느 호스팅사가 저렴한가"는 제품이 1개일 때의 질문이다. 에이전시는 다르다 — 관리 대상이 계속 늘어난다:
1. 하이파이브(자사 SaaS, PHP 전환 예정)
2. 에이전시 자체 홈페이지
3. **앞으로 수주할 고객사 프로젝트들** — 무엇이 될지 아직 모른다(PHP, 워드프레스, 정적사이트, 다른 스택일 수도 있음)

그래서 진짜 질문은 "어디가 싼가"가 아니라 **"프로젝트가 늘어날 때마다 계약/구조를 다시 짜야 하는가, 아니면 지금 만든 구조 위에 그냥 얹기만 하면 되는가"**다. 이건 상품 선택이 아니라 **아키텍처** 문제다.

---

## 2. "저가 공유호스팅"이 왜 한계가 되는가

카페24의 가장 싼 상품(리눅스/PHP 공유호스팅)은 보통 **계정 1개 = 사이트 1개** 구조다.
- 고객사 프로젝트가 하나 늘 때마다 상품을 새로 계약 → 결제/관리 포인트가 프로젝트 수만큼 늘어난다.
- 루트 권한이 없어 Node/Docker/특정 PHP 확장모듈처럼 프로젝트마다 다른 요구사항에 대응이 안 된다.
- 즉 "저가"의 대가가 "유연성 없음"이다 — 지금 하나 쓸 땐 안 보이지만, 프로젝트가 2~3개만 넘어가도 체감된다.

반대로 **루트 권한이 있는 VPS/클라우드 서버 1대**로 시작하면, 그 위에 사이트를 몇 개 올리든 추가 계약이 필요 없다. 초기비용은 공유호스팅보다 조금 높지만 "프로젝트당 한계"가 없다.

---

## 3. 권장 아키텍처 — VPS 1대 + 리버스 프록시 + 컨테이너

```
[인터넷]
   │
[Nginx 리버스 프록시] ── 도메인/서브도메인 기준으로 분기
   │
   ├── agency.com          → [Docker: 에이전시 홈페이지]
   ├── high5.agency.com     → [Docker: 하이파이브(PHP)]
   ├── clientA.com          → [Docker: 고객사 A 프로젝트]
   └── clientB.com          → [Docker: 고객사 B 프로젝트]
        (VPS/클라우드 서버 1대 안에서 전부 실행)
```

- **한 대의 VPS**(카페24든 어디든 루트 권한이 있는 가상서버)에 Nginx를 앞단 리버스 프록시로 두고, 도메인별로 요청을 분기한다.
- **프로젝트마다 Docker 컨테이너로 격리** — PHP 버전이 프로젝트마다 달라도, DB가 달라도, 의존성이 충돌해도 컨테이너 안에서만 존재하니 서로 침범하지 않는다.
- 이 구조의 핵심 효과: **"이 서버가 카페24냐 다른 곳이냐"가 더 이상 중요하지 않다.** 컨테이너 이미지 그대로 어디로든 옮길 수 있어 특정 호스팅사에 종속되지 않는다 — 이게 사용자가 우려한 "한계"를 없애는 장치다.

---

## 4. 단계별 성장 경로

| 단계 | 시점 | 인프라 | 비고 |
|---|---|---|---|
| **1단계** | 창업 초기, 프로젝트 0~수 개 | 카페24 VPS/클라우드 서버 **최소 사양 1대** | §3 구조로 하이파이브+에이전시 홈페이지부터 얹는다. 공유호스팅보다 조금 비싸지만 "프로젝트당 추가 계약" 없음 |
| **2단계** | 고객사 프로젝트 여러 개 확보 | 같은 VPS 사양업, 또는 트래픽 많은 프로젝트만 별도 서버 분리 | 아직 VPS 선에서 흡수 가능 |
| **3단계** | **법인 설립 + 서비스 본격화** | **관리형 클라우드(AWS/네이버클라우드/NHN Cloud 등)로 전환** | 아래 5절 참고 — 여기서부터는 명확히 클라우드로 가는 게 맞다 |

지금 카페24는 "최종 정답"이 아니라 **1단계 실행 장소**이고, 법인화·서비스 본격화 시점이 **클라우드 전환 트리거**다. 그 사이를 잇는 건 호스팅사가 아니라 §3의 **아키텍처(리버스프록시+컨테이너화)**다 — 이게 미래에도 안 바뀌는 뼈대이기 때문에, "한계"는 실제로는 호스팅사를 바꾸는 정도의 비용(이사)으로 끝난다.

---

## 5. "회사가 설립되고 서비스가 본격화되면 클라우드서버를 써야 하나?" — 예, 맞다

이 시점(3단계)에서 관리형 클라우드로 전환하는 걸 명확히 권장하는 이유:

1. **비즈니스 리스크가 커진다**: 고객사가 늘고 매출이 발생하면 장애/보안사고는 더 이상 "우리끼리 문제"가 아니라 계약된 고객의 문제가 된다. 클라우드는 이중화, 오토스케일링, 매니지드 DB, 자동백업, 모니터링을 상품으로 제공해 이 리스크를 흡수해준다.
2. **VPS는 애초에 이 단계용이 아니다**: 카페24 VPS는 "직접 관리하는 서버 1~2대"에 최적화된 선택이지, 여러 고객사의 SLA를 책임지는 단계의 안정성 요구사항을 위해 설계된 상품이 아니다.
3. **트래픽 변동 대응**: 특정 고객사 프로젝트가 이벤트/마케팅으로 트래픽이 갑자기 튀는 경우, VPS의 고정 사양보다 클라우드의 오토스케일링이 유리하다.
4. **작은 팀일수록 운영 시간이 아깝다**: 매니지드 서비스가 대신해주는 패치/백업/모니터링을, 초기 인력이 적은 에이전시가 직접 하는 건 기회비용이 크다.

그리고 이 전환이 "처음부터 다시 만들기"가 아니라 **"이사"**로 끝나는 이유가 바로 1~2단계에서 잡아둔 **Docker 컨테이너화** 덕분이다 — 컨테이너 이미지를 그대로 AWS ECS, 네이버클라우드 컨테이너 서비스 등으로 옮기면 된다. **지금 컨테이너화를 안 해두면 이 시점에 처음부터 다시 만들어야 하므로, 지금 단계에서부터 컨테이너 구조를 잡아두는 것 자체가 이번 제안의 핵심 투자다.**

---

## 6. 비용 관점 — 솔직한 정리

- "카페24가 제일 저렴하다"는 판단이 **공유호스팅 기준**이라면, VPS로 올라가는 순간 그 저렴함은 줄어든다 — 이 부분은 숨기지 않는 게 맞다.
- 다만 프로젝트 수가 늘수록 공유호스팅은 계약을 프로젝트 수만큼 곱해서 늘려야 하지만, VPS는 한 대가 흡수한다 — **에이전시로 프로젝트가 2~3개만 넘어가도 VPS 쪽 총비용이 더 유리해지는 손익분기점**이 존재한다. 지금 막 시작하는 시점에도, 첫 고객사 프로젝트 한두 개만 더 들어오면 금방 이 손익분기를 넘는다.

---

## 7. 지금 당장 할 일 (체크리스트)

1. 카페24 "클라우드 서버(가상서버호스팅)" 상품 페이지에서 **최소 사양** 견적 확인 (계약 전 최신 사양/가격은 공식 홈페이지에서 재확인)
2. VPS에 Docker + Nginx 설치
3. Nginx를 리버스 프록시로 구성 — 도메인/서브도메인별 라우팅 규칙 준비
4. 하이파이브(PHP 전환분)를 Docker 컨테이너 하나로 패키징해 첫 사이트로 얹기
5. 에이전시 홈페이지를 두 번째 컨테이너로 얹기
6. 이후 고객사 프로젝트가 생길 때마다 "컨테이너 하나 추가 + Nginx 라우팅 규칙 한 줄"로 확장 — 이게 이 구조의 핵심 이득
