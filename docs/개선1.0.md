# 개선 1.0 — "노션만큼 자유롭게, 지라만큼 편리하게, 그러나 심플하게"

## Context

지금 업무 목록(`/tasks`)은 ID/제목/담당자/등록일자/목표일/비고/작업시간/상태 8개 컬럼이
전부 하드코딩되어 있고(`src/app/tasks/page.tsx`), 이 구조를 벗어나 항목을 추가/삭제할
방법이 없다. 사용자가 원래 그리던 방향은 "노션처럼 업무 리스트에 항목(속성/컬럼)을
자유롭게 추가·삭제하면서도, 지라처럼 상태·담당자 관리가 편리하고, 노션만큼 복잡해지지는
않는" 앱이었다. 최근 세션(main에 이미 병합됨)에서 이미 **프로젝트별 상태(칸반 단계)
커스터마이징** 기능이 구현되어 있는데(`ProjectStatus` 모델, `useProjectStatuses` 훅,
`/api/projects/[id]/statuses` 라우트), 이것이 정확히 "노션식 자유도 + 지라식 관리"의
축소판 선례다. 이번 계획은 같은 패턴을 "커스텀 필드(속성)"로 확장해, 업무 목록에
사용자가 원하는 열을 자유롭게 추가/삭제/편집할 수 있게 만드는 것을 목표로 한다.

## 핵심 아이디어: 프로젝트별 커스텀 필드 (Task Custom Fields)

기존 `ProjectStatus`와 완전히 동일한 설계 패턴을 재사용한다: 프로젝트 단위로 정의를
저장하는 테이블 + 태스크별 값을 저장하는 테이블(EAV 방식) + 훅 + API 라우트.

### 1. 데이터 모델 (Prisma)

`prisma/schema.prisma`에 두 모델 추가:

```prisma
model ProjectField {
  id        Int      @id @default(autoincrement())
  projectId Int
  name      String              // 노출 라벨 (예: "고객사", "예상공수")
  type      String              // TEXT | NUMBER | DATE | SELECT | CHECKBOX
  options   String?             // SELECT 타입일 때 콤마구분 선택지 (URGENT,WEEKEND처럼)
  order     Int      @default(0)
  createdAt DateTime @default(now())
  project   Project  @relation(fields: [projectId], references: [id])
  values    TaskFieldValue[]

  @@unique([projectId, name])
}

model TaskFieldValue {
  id      Int          @id @default(autoincrement())
  taskId  Int
  fieldId Int
  value   String?      // 모든 타입을 문자열로 저장(단순함 우선), 프론트에서 타입별 파싱/렌더
  task    Task         @relation(fields: [taskId], references: [id], onDelete: Cascade)
  field   ProjectField @relation(fields: [fieldId], references: [id], onDelete: Cascade)

  @@unique([taskId, fieldId])
}
```

- 필드 개수 상한(예: 프로젝트당 최대 10개)을 API 레벨에서 강제해, `ProjectStatus`의
  "최소 1개, 최대 15개" 검증과 동일한 방식으로 복잡도를 통제한다.
- 필드 타입은 5종(텍스트/숫자/날짜/선택/체크박스)으로 제한 — 노션처럼 블록/관계형/수식
  등 무한 확장은 의도적으로 배제해 "심플함"을 지킨다.

### 2. API 라우트

`src/app/api/projects/[id]/fields/route.ts` 신설 — `statuses/route.ts`와 동일한 구조:
- `GET`: 프로젝트의 필드 정의 목록 조회 (없으면 빈 배열, 상태처럼 강제 기본값 없음)
- `PUT`: ADMIN/LEADER만 필드 정의 전체 교체(추가/삭제/이름변경/순서변경), 트랜잭션 처리

`src/app/api/tasks/[id]/fields/route.ts` 신설 (또는 기존 `tasks/[id]/route.ts`의 PATCH에
통합):
- 개별 태스크의 필드 값 upsert (`taskId+fieldId` unique 활용)

### 3. 프론트 — 재사용 패턴

- `src/hooks/useProjectFields.ts`: `useProjectStatuses.ts`를 그대로 본떠서 작성
  (`getFields(projectId)`, 캐싱 구조 동일).
- `src/types/index.ts`에 `ProjectField`, `TaskFieldValue` 타입 추가, `Task.fieldValues?`
  옵셔널 배열 추가.

### 4. UI — 업무 목록 (`src/app/tasks/page.tsx`)

- 고정 8개 컬럼 뒤에 현재 프로젝트의 커스텀 필드를 동적 컬럼으로 렌더링.
- 헤더 맨 끝에 노션 스타일의 **"+ 속성 추가"** 버튼 → 작은 팝오버(이름/타입/선택지 입력)로
  즉석 추가. 삭제는 헤더 컬럼에 마우스 오버 시 나오는 `x` 버튼.
- 셀은 타입별 인라인 편집(텍스트=input, 숫자=number input, 날짜=date input, 선택=select,
  체크박스=checkbox) — 기존 담당자/상태 셀의 인라인 편집 UX(`statusSelect` 등)와
  동일한 상호작용 원칙을 따른다.
- 프로젝트 미선택(전체 보기) 상태에서는 커스텀 필드 컬럼은 숨김(프로젝트별 정의라 여러
  프로젝트가 섞이면 의미가 없음) — `selectedProject`가 있을 때만 노출.

### 5. UI — 업무 상세 (`src/app/tasks/[id]/page.tsx`)

- "기본 정보" 카드 아래 "속성" 섹션 추가, 해당 프로젝트의 커스텀 필드를 라벨-값 쌍으로
  표시/편집(목록의 인라인 편집과 동일한 컴포넌트 재사용).

### 6. 칸반 (`src/components/kanban/KanbanColumn.tsx`)

- 1단계에서는 손대지 않음(범위 통제). 필요 시 2단계에서 "카드에 표시할 필드 1개 선택"
  같은 최소 기능만 추가 검토.

### 7. 기존 라벨(URGENT/WEEKEND/EMERGENCY)과의 관계

- 지금 하드코딩된 라벨은 그대로 둔다(이미 안정적으로 쓰이는 기능). 커스텀 필드와
  중복 개념이지만, 무리하게 통합하지 않고 "라벨 = 앱 전역 고정 태그", "커스텀 필드 =
  프로젝트별 자유 속성"으로 역할을 분리해 마이그레이션 리스크를 없앤다.

## 단계별 진행 (Phasing)

1. **Phase 1**: 스키마 + API + 업무 목록에서 필드 추가/삭제/편집.
2. **Phase 2**: 업무 상세 페이지에 속성 섹션 반영.
3. **Phase 3(선택)**: 칸반 카드에 필드 노출, 필드 타입 추가(예: 사람 참조형).

## 검증 방법

- `npx tsc --noEmit`으로 타입 오류 없는지 확인(빌드/린트는 환경 제약으로 미실행 관례 유지).
- `npx prisma migrate dev` (또는 환경에 맞는 방식)로 새 모델 마이그레이션 적용 확인.
- 브라우저에서: 프로젝트 선택 → "+ 속성 추가"로 텍스트/선택형 필드 생성 → 목록에 컬럼
  노출 확인 → 값 입력 후 새로고침해도 유지되는지 확인 → 필드 삭제 시 컬럼과 값이
  같이 사라지는지 확인.
