## 1. "Jira/Notion보다 가벼운 도구" 원칙 재점검

### 1-1. 무거워진 지점 (SaaS화로 인한 확장)
초기엔 사내 업무관리 도구였다가, 이후 멀티테넌시(Organization) · 슈퍼관리자 · 2FA · 세션관리 · 감사로그 · 플랜별 메뉴 게이팅까지 갖춘 **미니 SaaS 플랫폼**으로 확장됐다(`docs/하이파이브_08_v1.md` §2, §4.8, §4.9). 이 자체는 "여러 회사에 판매 가능한 제품"으로 가는 데 필요한 투자였지만, 다음은 "가벼움"이라는 원래 가치와 계속 충돌할 수 있는 지점이다:

- **가입 직후 온보딩 부재**: `/register` → 가입 완료 후 바로 `/dashboard`로 들어가는데, `dashboard/page.tsx`는 프로젝트/업무가 하나도 없으면 "오늘 예정된 업무가 없습니다" 같은 빈 상태만 보여준다. 프로젝트를 만들고 팀원을 초대하라는 다음 행동 유도가 없다 — Jira/Notion류가 아니라 오히려 "빈 화면"에 더 취약해지는 지점(SaaS 초회원의 이탈 요인 1순위).
- **plan 게이팅이 아직 "가벼움"보다 "제약"으로 느껴질 수 있음**: `SystemConfig.planFeatures`로 FREE plan은 통계/구글캘린더연동/외부연동이 막혀 있다(`하이파이브_08_v1.md` §4.9). 무료 사용자가 "가벼운 대안"으로 써보려는 순간 기능이 잠겨 있으면 첫인상에서 이탈할 수 있다 — FREE 플랜 기능 구성 재검토 여지.

### 1-2. 반대로, "가벼운 도구"가 갖춰야 할 기본기 중 아직 빠진 것
실제 코드를 확인한 결과(스키마·API·페이지 전수), 아래는 실재하는 갭이다:

| 갭 | 확인 근거 | 왜 중요한가 |
|---|---|---|
| 업무 우선순위 필드 없음 | `prisma/schema.prisma`의 `Task`에 `priority` 없음 | 업무가 쌓이면 "뭐부터 할지"를 구분할 방법이 목표일뿐 — Trello/Notion도 기본 제공하는 최소 기능 |
| 개인화 뷰("내 업무함") 없음 | `src/app/tasks/page.tsx`에 담당자 필터는 있으나 "내 업무만 보기" 고정 탭/기본값 없음 | 팀 인원이 늘수록 전체 목록에서 매번 필터링해야 함 — 가벼운 도구일수록 "로그인하면 바로 내 일이 보인다"가 중요 |
| 알림 개별 읽음 처리 없음 | `src/app/api/notifications/`에 `route.ts`(목록)와 `read-all/route.ts`만 존재, 개별 `PATCH /[id]/read` 없음 | 알림을 하나 확인하면 전체가 읽음 처리됨 — 알림이 늘어날수록 불편이 커지는 구조적 이슈 |
| 댓글 알림 없음(멘션만) | `docs/하이파이브_08_v1.md` §4.7 — 담당자/상태 변경만 알림 트리거, 일반 댓글 등록 알림 없음 | 협업 도구의 기본 기대치인데 빠져 있음 |

### 1-3. 권장 — "가벼움 가드레일" 원칙
신규 기능을 얹을 때마다 아래 체크리스트를 통과해야 "가벼움"이 지켜진다고 제안한다:
1. 기본값이 OFF거나, 안 써도 기존 화면이 그대로 단순하게 보이는가(plan 게이팅/설정 토글로 숨길 수 있는가)
2. 신규 개념(모델)을 늘리기 전에 기존 모델 확장으로 해결되지 않는지 먼저 검토(`ProjectStatus`/`ProjectField`처럼 "정의 테이블 + 값 테이블" 패턴이 이미 있음 — 신규 기능도 이 패턴을 우선 재사용)
3. 1-2절의 "빠진 기본기"부터 채우는 게 새로운 SaaS 관리 기능보다 ROI가 높다 — 우선순위/내 업무함/개별 알림읽음은 스키마 변경이 적고 체감 효과가 큰 항목이라 **가장 먼저 다룰 것을 권장**.

## 2. 구글시트 연동 실행안

### 2-1. 현재 자산 / 갭 (재확인)
- 있음: `src/app/api/tasks/export/route.ts`가 `xlsx`(SheetJS)/`papaparse`로 업무 데이터를 표로 직렬화하는 로직 보유.
- 없음: `googleapis` 등 Google API 클라이언트, Google OAuth/서비스계정 인프라 전무(`docs/ROADMAP_AI_AUTOMATION.md` §4 확인, 코드에도 없음을 재확인).

### 2-2. 범위 확정 제안
**1단계 "내보내기 전용"부터 시작**을 권장한다 — 앱에서 시트를 편집하면 다시 반영하는 양방향 동기화는 충돌 처리(누가 이겼는지), 실시간 감지(Google Sheets API에 webhook이 없어 폴링 필요) 등 복잡도가 급격히 올라간다. "관리자가 버튼을 누르면 지정된 시트에 최신 업무 목록이 갱신된다" 수준이면 지금 있는 `export` 로직만 확장해도 된다.

### 2-3. 인증 방식 — 서비스 계정(Service Account) 권장
- 조직마다 사용자가 Google 계정으로 로그인해 동의하는 **사용자별 OAuth**는 구현이 훨씬 크다(동의화면 심사, 토큰 갱신, 사용자 이탈 시 처리).
- 대신 **회사 소유의 서비스 계정 키 하나**를 조직 관리자가 등록하고, "이 시트에 편집 권한을 서비스 계정 이메일로 공유"만 안내하면 OAuth 흐름 없이 즉시 사용 가능 — 구축 속도가 훨씬 빠르다.
- 단, 이 방식은 "회사가 지정한 시트 하나"에 최적화되어 있고, "각 사용자가 각자 본인 시트에 연동"하는 형태는 어렵다 — 실제 착수 전에 어느 쪽 사용성을 원하는지 확정 필요(대부분의 중소기업 사용 패턴상 "회사 공용 시트"가 자연스러울 것으로 예상).

### 2-4. 구현 스케치 (참고용, 상세 설계 아님)
- `googleapis` 패키지 추가.
- `src/lib/google-sheets.ts`(신규): 서비스계정 키로 인증 → `spreadsheets.values.update`로 업로드하는 헬퍼.
- 조직별 설정(시트 ID, 서비스계정 키 JSON)은 `Integration`이나 최근 세션에서 논의된 `AiSettings` 패턴처럼 "조직별 설정 테이블 + 암호화 저장"을 재사용. 서비스계정 키는 반드시 암호화 저장(AES-256-GCM, `NEXTAUTH_SECRET` 기반 파생 키 사용하는 패턴을 다른 시크릿 저장에도 이미 적용해본 적 있음 — 동일 패턴 재사용).
- 신규 API 예: `PUT /api/settings/google-sheets`(설정 저장, ADMIN), `POST /api/settings/google-sheets/sync`(수동 동기화 실행) — 기존 `tasks/export`의 데이터 직렬화 로직을 그대로 재사용.
- `/settings/integrations`처럼 관리자 설정 페이지에 "구글시트 연동" 카드 추가.

### 2-5. 리스크 / 코드 밖 준비물
- Google Cloud Console에서 프로젝트 생성 + Sheets API 활성화 + 서비스계정 발급은 코드 작업이 아니라 콘솔 작업 — 사용자가 직접 처리해야 함.
- 서비스계정 키 유출 시 해당 시트뿐 아니라 계정에 공유된 모든 자원이 위험 — 조직당 별도 서비스계정을 강제하거나(운영 부담 증가), 최소 권한 원칙을 문서화해 안내할 필요.

## 3. 전체 고도화 로드맵 (우선순위 재정리)

기존 `docs/ROADMAP_AI_AUTOMATION.md`/`docs/AUTOMATION_DESIGN.md`의 분석과 `docs/하이파이브_08_v1.md` 부록 A(문서에는 있으나 코드엔 없는 항목)를 하나로 모아 3갈래로 재정리한다.

| 갈래 | 항목 | 우선순위 근거 |
|---|---|---|
| **A. 협업 강화(경량 개선)** | 우선순위 필드, "내 업무함" 뷰, 알림 개별 읽음, 댓글 알림 | 스키마 변경 최소, 체감 효과 큼, "가벼움" 원칙에도 부합 → **최우선** |
| | 온보딩 흐름(가입 직후 안내) | 신규 SaaS 가입자 이탈 방지, UI 위주 작업 |
| **B. 자동화/AI** | 외부연동 확장(기존 `dispatch()`/`Integration` 인프라 위에 트리거만 추가) | 인프라 투자 가장 적음 → B 갈래 중 최우선 |
| | 주간보고 AI 자동생성 | 이 프로젝트에서 LLM을 처음 도입하는 항목으로 적합(기존 `stats.service.ts` 집계 재사용) |
| | 작업자별 AI 자동배정 | 주간보고에서 만든 LLM 연동 기반 위에서 진행. 워크로드 기반 "추천"부터 시작 후 LLM 판단 얹기 |
| | 구글시트 연동(§2) | 위 항목들과 기술적으로 독립적 — 병렬 진행 가능하나 Google Cloud 콘솔 준비가 별도 필요 |
| **C. 플랫폼 성숙도** | 보안 마감(조직 간 데이터 격리 IDOR 잔여 점검 — `findUnique`가 `organizationId` 필터 없이 쓰인 API 재점검) | SaaS로 여러 회사 데이터를 담는 이상 최우선 리스크 항목, 사업 개시 전 필수 |
| | 법적고지(이용약관/개인정보처리방침) + 가입 동의 | 실서비스 오픈 전 필수 |
| | 이메일 발송 인프라(가입/알림 메일) | 사용자 커뮤니케이션 채널 확보 |

**착수 권장 순서**: C(보안 마감) → A(경량 협업 개선) → B-외부연동확장 → B-주간보고 → B-자동배정 → 구글시트(병렬 가능). 보안을 가장 앞에 둔 이유는 이미 여러 조직의 데이터가 한 DB에 공존하는 멀티테넌시 구조이기 때문 — 신규 기능보다 데이터 격리 재검증이 리스크 대비 우선순위가 높다.

## 4. 카페24 저비용 호스팅 검토

> **주의**: 아래 상품 구분은 일반적인 카페24 라인업 특성에 대한 검토이며, 실제 최신 요금/사양은 시점에 따라 바뀔 수 있다. **계약 전 카페24 공식 홈페이지에서 최신 정보를 반드시 재확인**해야 한다.

### 4-1. 왜 "저렴한 호스팅"이 바로 안 맞을 수 있는가
High5는 Next.js **App Router + SSR**(서버 컴포넌트, API 라우트, NextAuth 세션 등)로 동작한다. 이건 정적 파일만 서빙하면 되는 게 아니라 **상시 Node.js 프로세스**가 떠 있어야 한다. 카페24의 대표적인 "저렴한 호스팅"(일반 웹호스팅류)은 대부분 PHP 전용 공유호스팅이라 Node 런타임을 지원하지 않는다 — 이 상품군은 대상에서 제외해야 한다.

### 4-2. 검토 대상이 될 수 있는 카페24 상품군
Node를 직접 설치해 실행할 수 있는 **VPS/클라우드 서버(가상서버호스팅) 계열**이 실질적 후보다. 이 경우:
- 장점: 트래픽이 적은 소규모 서비스 초기엔 Railway보다 월 비용이 낮아질 수 있다.
- 단점: Railway가 자동으로 해주던 것(`railway.json`의 빌드/배포/헬스체크/재시작 정책)을 전부 직접 구축해야 한다 — 배포 스크립트, 프로세스 매니저(PM2 등), 무중단 배포, 롤백, 모니터링을 스스로 운영. 즉 "서버비는 아낄 수 있지만 운영 부담은 늘어난다."

### 4-3. 트레이드오프 표

| 항목 | Railway (현재) | 카페24 VPS/클라우드서버 (이전 시) |
|---|---|---|
| Node 런타임 | 기본 지원(Nixpacks) | 직접 설치/관리 |
| 배포 자동화 | git push → 자동 빌드/배포 | 직접 CI/CD 구축 필요(GitHub Actions 등) |
| 헬스체크/재시작 | `railway.json`으로 선언적 설정 | PM2 등으로 직접 구성 |
| DB(Postgres) | 플러그인 추가로 즉시 연결 | 별도 설치/백업 정책 직접 관리(또는 카페24 DB 상품 별도 계약) |
| 비용 | 트래픽/사용량 비례, 무료/저가 티어 존재 | 고정 월비용, 사양 낮을수록 저렴하나 최소 사양 이상 필요 |
| 빌드 부담 | Railway 빌드 서버에서 처리 | 서버 사양이 낮으면 `next build` 자체가 버거울 수 있음 (아래 4-4) |

### 4-4. 이전 시 코드/구성 변경 포인트
저사양 서버로 옮기기로 결정한다면 아래는 실제로 손대야 하는 지점이다:
1. **`next.config.ts`에 `output: 'standalone'` 추가** — 현재는 미설정 상태(`reactStrictMode`, `optimizePackageImports`만 있음). standalone 빌드는 필요한 의존성만 골라 산출물을 만들어 배포 용량/시작 메모리를 줄인다. 저사양 서버에선 사실상 필수에 가깝다.
2. **빌드를 서버에서 직접 하지 않기** — `next build`는 메모리를 많이 쓴다(대형 프로젝트일수록). 저사양 VPS에서 직접 `npm run build`를 돌리면 OOM 위험이 있다. 대안: GitHub Actions 등 CI에서 빌드 후 `standalone` 산출물만 서버로 전송(rsync/scp)해 `node server.js`로 구동.
3. **`npm start`의 `prisma db push --accept-data-loss` 분리** — 현재 `package.json`의 `start` 스크립트가 매 시작마다 `db push`를 실행한다(Railway 환경 전제). 상시 재시작이 잦은 저사양 서버에서 이 스크립트를 그대로 쓰면 실수로 운영 DB 스키마가 매번 재적용될 위험이 있다 — 배포 파이프라인에서 "마이그레이션은 배포 시 1회만" 실행하도록 분리 권장.
4. **PM2 등 프로세스 매니저 신규 도입** — Railway의 `restartPolicyType: ON_FAILURE`를 대체할 상시 실행/재시작 설정 필요.
5. **헬스체크 엔드포인트(`/api/health`)는 이미 있음** — 로드밸런서/모니터링 붙일 때 그대로 재사용 가능.

### 4-5. PHP 전환 검토 — "성능"이 아니라 "재작성 규모"가 진짜 비용

VPS 비용조차 중소기업엔 부담이라 PHP 공유호스팅(카페24 저가 상품)까지 검토한다면, 핵심 질문을 성능과 비용 두 가지로 나눠서 봐야 한다.

**성능 자체는 문제되지 않는다.** High5는 영상 인코딩·대량 연산 같은 CPU 집약 작업이 없는 전형적인 CRUD 업무관리 앱이다(업무 목록 조회, 상태 변경, 댓글 등). 이런 워크로드에서 병목은 언어(PHP vs Node)가 아니라 대부분 **DB 쿼리**다. PHP-FPM은 요청마다 짧게 살고 죽는 프로세스 모델이라 오히려 공유호스팅처럼 메모리가 제한된 환경에 최적화되어 있다 — 카페24 같은 곳에 PHP 전용 저가 상품이 존재하고 Node 상품은 없는 이유이기도 하다. 중소기업 내부 도구 수준의 동시 사용자 규모(수십~수백 명)라면 PHP 공유호스팅으로도 체감 성능 저하는 없다고 봐도 된다.

**진짜 비용은 "전면 재작성"이다.** 지금 코드베이스는 Next.js(React 프론트 + App Router SSR) + Prisma/PostgreSQL + NextAuth로 이미 완성되어 있다(`docs/하이파이브_08_v1.md` 기준 페이지 26개, API 60개, 데이터 모델 25개, 그룹업무/자동시간카운트/프로젝트별 커스텀 상태 같은 복잡한 비즈니스 로직 포함). PHP로 옮긴다는 건 설정 변경이 아니라 **이 전체를 처음부터 다시 만드는 것**과 같다:
- 프론트엔드(React 컴포넌트 전체)를 PHP 템플릿 또는 별도 SPA+PHP API로 재작성
- 인증(NextAuth JWT+2FA)을 PHP 세션/라이브러리로 재구현
- Prisma ORM으로 짜인 모든 쿼리/트랜잭션을 PHP ORM(Laravel Eloquent 등)으로 재작성
- 카페24 공유호스팅은 보통 MySQL 기준이라 PostgreSQL 전용 기능을 쓰는 부분이 있다면 DB 자체도 이관 검토 필요

규모감으로 보면 이건 "몇 주"가 아니라 **처음부터 다시 개발하는 수준의 프로젝트**다. 호스팅비 차이(VPS/Railway 월 몇만 원 vs PHP 공유호스팅 월 몇천~1만 원대)로 절약되는 금액이, 재작성에 들어가는 개발 리소스(비용)를 회수하는 데 걸리는 기간을 감당할 만한지부터 따져야 한다 — 대부분의 경우 수년 치 호스팅비 차액을 재작성 비용이 넘어선다.

### 4-6. 권장
- **PHP 전환은 권장하지 않는다** — 성능이 아니라 순수하게 "재작성 비용 > 절감되는 호스팅비"의 문제. PHP 개발 인력이 이미 사내에 있고 Node 스택을 유지보수할 인력이 전혀 없는 경우가 아니라면 실익이 없다.
- 비용이 진짜 목표라면 **기술 스택은 유지한 채 더 싼 Node 호스팅**을 찾는 쪽이 합리적이다. 우선순위:
  1. **Vercel 무료/하비 티어** — Next.js 제작사 플랫폼이라 별도 튜닝 없이 지금 코드 그대로 배포 가능, 트래픽이 적은 중소기업 내부 도구 수준이면 무료 티어로도 충분할 가능성이 높다(단, 서버리스 특성상 DB 커넥션 풀링 등 몇 가지 설정은 확인 필요).
  2. **카페24 라이트서버/클라우드 서버 중 최소 사양(1vCPU/1GB급)** — 4-4에서 정리한 `standalone` 빌드 등 최적화를 적용하면 저사양에서도 이 정도 앱은 충분히 구동 가능. VPS 비용 부담이 크다면 최소 사양 상품부터 견적을 받아보는 것을 권장.
  3. Railway를 트래픽이 실제로 늘어날 때까지 유지 — 무료/저가 티어 안에서 해결되는 규모라면 지금 당장 옮길 필요는 없다.
- 즉 "성능 걱정 없이 비용을 낮추고 싶다"는 목표에는 PHP 재작성보다 **위 3가지 중 하나로 지금 스택을 그대로 옮기는 것**이 리스크와 비용 모두 훨씬 낮다.
