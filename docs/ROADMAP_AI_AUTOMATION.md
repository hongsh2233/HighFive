# AI/자동화 로드맵 (현황 분석)

> 이 문서는 즉시 착수할 작업 목록이 아니라, 향후 4가지 방향에 대한 **현황 분석과
> 참고용 계획**이다. 사용자가 "지금 당장 할건 아니고 현황 분석후 계획 세워줘"라고
> 명시한 요청에 따라 작성됐다. 실제 착수 시에는 각 항목에 대해 별도의 상세 설계와
> `dev-workflow` 절차(계획 승인 → 구현 → 문서화)를 다시 거쳐야 한다.

## 공통 인프라 갭

4가지 방향 중 여러 개가 같은 미비 인프라를 공유한다. 아래 3가지 중 하나를 먼저
구축하면 여러 항목이 동시에 앞당겨진다.

- **LLM API 연동이 전무하다.** `package.json`에 `openai`/`anthropic`/`@anthropic-ai` 등
  AI SDK가 하나도 없고, `src` 어디에도 LLM 호출 코드가 없다. "주간보고 자동생성"과
  "AI 자동배정" 둘 다 이 기반이 있어야 시작할 수 있다 — 즉 이 둘은 사실상 하나의
  선행 작업(LLM 클라이언트 도입)을 공유한다.
- **스케줄링(cron/job queue) 인프라가 전무하다.** `node-cron`, `bullmq`, `agenda` 등
  어떤 것도 의존성에 없다. "주간"이라는 주기성을 가지려면 Vercel Cron이든 Railway의
  스케줄 트리거든 별도로 도입해야 한다(현재 배포는 Railway, `railway.json` 기준).
- **Google OAuth 인프라가 전무하다.** `src/lib/auth.ts`는 NextAuth Credentials
  프로바이더만 등록되어 있고, `GOOGLE_CLIENT_ID`/`SECRET`도 토큰 저장 모델도 없다.
  기존 "구글캘린더연동"(`src/app/settings/calendar-sync/`)은 순수 iCal 구독 URL
  발급일 뿐 Google API를 전혀 호출하지 않으므로, 재사용 가능한 OAuth 기반이 없다.
  구글시트 연동은 이 기반을 0부터 만들어야 한다.

## 1. 주간보고 AI 자동생성

**현재 상태(재사용 가능한 것)**
- `src/lib/services/stats.service.ts`의 `getMonthlySummary()`(4~24번 줄, 상태별 업무
  개수·완료 건수를 `prisma.task.groupBy`로 집계)와 `getWorkloadStats()`(작업자별
  시간/업무 수)가 이미 있다. 월 단위지만 날짜 범위(`from`/`to`)를 주 단위로 바꾸는
  정도의 수정으로 "이번 주 데이터"를 뽑아낼 수 있다.
- `GET /api/stats/summary`, `GET /api/stats/workload` 라우트가 이 집계를 API로
  이미 노출하고 있어, 별도 쿼리를 새로 짤 필요 없이 파라미터만 주 단위로 확장하면
  됨.

**없는 것**
- 주 단위 집계 쿼리(현재는 월 단위만 지원).
- LLM API 연동 자체(위 공통 갭 참고).
- 리포트를 자동으로 트리거하는 스케줄러, 결과를 전달할 채널(이메일/Slack/사내
  공지 등 — `src/lib/integrations.ts`의 기존 dispatch 채널을 재사용할 수도 있음).
- 리포트 결과를 저장/열람할 UI 또는 모델(현재 어떤 리포트 이력도 DB에 남지 않음).

**난이도**: 중 (데이터 집계는 쉽지만 LLM 연동 + 스케줄러가 새 인프라)

**대략적 방향**: 주 단위 집계 함수를 `stats.service.ts`에 추가 → 집계 결과를 프롬프트로
구성해 LLM에 요약 요청 → 결과를 새 모델(예: `WeeklyReport`)에 저장하고 `/stats`
또는 새 페이지에서 열람, 필요 시 `integrations.ts`의 기존 채널로 발송. 실제 착수 시
"누구에게, 어떤 범위로(전체/프로젝트별/개인별) 보고할지" 요구사항을 먼저 확정해야 함.

## 2. 작업자별 업무 분석 후 AI 자동배정

**현재 상태(재사용 가능한 것)**
- `GET /api/stats/workload`(`src/app/api/stats/workload/route.ts`)가 작업자별
  `totalTasks`/`completedTasks`/`totalHours`/`averageHoursPerTask`를 이미 계산한다.
  현재는 통계 대시보드 표시 전용이지만, 이 로직을 배정 시점에 재사용해 "현재 부하가
  가장 낮은 작업자" 같은 신호로 쓸 수 있다.

**없는 것**
- 업무 배정 자체가 `POST /api/tasks`에서 `workerId`가 완전 수동 필수값이다
  (`src/app/api/tasks/route.ts:88`, `if (!title || !workerId || !registrantId)`) —
  자동/추천 배정 개념이 코드 어디에도 없다.
- `ProjectMember` 모델(`prisma/schema.prisma`)에 역량/스킬/가중치 필드가 전혀 없어,
  단순 업무량 균형(workload balancing) 이상의 "적합도" 판단은 스키마 확장이 필요.
- LLM API 연동(공통 갭).

**난이도**: 상 (배정은 사람이 최종 판단해야 하는 민감한 영역이라, "자동 배정"보다는
"추천"으로 시작하는 게 안전 — UX/신뢰 설계가 기술 구현보다 더 중요할 수 있음)

**대략적 방향**: 1단계로 업무 등록 폼(`/tasks/create`)에서 담당자 select 옆에
"추천 담당자"(워크로드 최저 순 N명) 배지를 보여주는 것부터 시작 — LLM 없이도
`GET /api/stats/workload` 재사용만으로 가능한 저비용 1차 개선. 2단계로 LLM에
업무 제목/설명 + 각 작업자의 최근 업무 이력을 넣어 "적합도" 판단을 추가하는 것은
스키마 확장과 LLM 연동이 모두 필요한 별도 트랙.

## 3. 외부 연동 및 자동화

**현재 상태(재사용 가능한 것)**
- `src/lib/integrations.ts`의 `dispatch()`(44~80번 줄)가 SLACK/JANDI/TEAMS/
  TELEGRAM/KAKAO 5개 채널에 대해 상태 변경 알림을 이미 발송하고, `Integration`
  모델(`prisma/schema.prisma`)이 채널별 설정(`webhookUrl`/`botToken`/`chatId`/
  `isEnabled`)을 DB에 저장 + env 폴백까지 지원한다 — 아웃바운드 알림 인프라의
  기본기는 이미 갖춰져 있다.

**없는 것**
- 현재는 "업무 상태 변경 시 알림"이라는 단일 하드코딩 트리거뿐, 일반화된
  트리거/조건/액션 규칙 엔진이 아니다(예: "특정 라벨이 붙으면", "목표일이 지나면"
  같은 조건부 자동화는 지원하지 않음).
- 인바운드 웹훅(외부에서 이 앱으로 이벤트를 보내는 경로)이 전혀 없다 — 현재는
  전부 아웃바운드뿐.
- 자동화 규칙을 사용자가 직접 구성하는 UI(현재 `/settings/integrations`는 채널별
  연결 설정만 가능, "규칙"이라는 개념 자체가 없음).

**난이도**: 중 (기존 dispatch 인프라 위에 트리거 종류를 늘리는 정도는 상대적으로
쉬움. 완전한 규칙 엔진 + 인바운드 웹훅까지 가면 상 난이도)

**대략적 방향**: 먼저 트리거 종류를 몇 개 더(목표일 임박, 라벨 부착 등) 하드코딩으로
늘려 실사용 패턴을 파악한 뒤, 필요하면 `AutomationRule`(트리거 타입 + 조건 + 채널)
같은 모델을 추가해 일반화. 인바운드 웹훅은 별도 트랙(보안/인증 설계 필요).

> **구체 설계**: Phase 1(트리거 확장)/Phase 2(규칙 엔진) 스키마·API·파일 단위
> 상세 설계는 `docs/AUTOMATION_DESIGN.md` 참고.

## 4. 구글시트 연동

**현재 상태(재사용 가능한 것)**
- `src/app/api/tasks/export/route.ts`가 이미 `xlsx`(SheetJS)로 `.xlsx` 파일을,
  `papaparse`로 CSV를 생성해 다운로드시킨다 — "업무 데이터를 표 형태로 직렬화하는"
  로직 자체는 있다.

**없는 것**
- `googleapis`/`google-auth-library` 등 Google API 클라이언트가 `package.json`에
  전혀 없다.
- Google OAuth 인프라 자체가 없다(공통 갭 참고) — 기존 "구글캘린더연동"은 iCal
  구독 URL만 발급할 뿐이라 재사용할 토큰/인증 코드가 하나도 없다. 시트 연동은
  Calendar 연동과 별개로 0부터 OAuth 동의화면 등록, 스코프 설정, 토큰 저장/갱신을
  구축해야 한다.

**난이도**: 중~상 (Google Cloud 콘솔에서 OAuth 앱 등록 같은 코드 밖 작업이 필요하고,
토큰 저장/갱신은 보안 설계가 필요 — 순수 "내보내기(export)"만 지원할지, 양방향
동기화까지 할지에 따라 난이도가 크게 갈림)

**대략적 방향**: 범위를 좁혀서 "내보내기 전용"으로 시작하는 게 현실적 — 이미 있는
`export` 라우트의 xlsx 생성 결과를 Google Sheets API(`spreadsheets.values.update`)로
업로드하는 것만 구현하면 양방향 동기화보다 훨씬 단순함. 이 경우도 서비스 계정(Service
Account) 방식을 쓰면 사용자별 OAuth 동의 없이 구현할 수 있어, 사용자별 OAuth보다
훨씬 빠르게 시작 가능 — 실제 착수 시 "회사 소유 시트 하나에 관리자가 내보내는" 용도인지
"각 사용자가 본인 시트에 연동"하는 용도인지부터 확정 필요.

## 권장 착수 순서

현재 코드베이스 기준 의존관계와 난이도를 종합하면:

1. **외부 연동/자동화 확장** — 기존 `dispatch()`/`Integration` 인프라 위에 트리거를
   늘리는 정도라 가장 인프라 투자가 적고 빠르게 가치를 낼 수 있음.
2. **주간보고 AI 자동생성** — 이 프로젝트에서 LLM 연동을 처음 도입하는 항목으로
   삼는 것을 추천. 여기서 구축한 LLM 클라이언트/설정 패턴을 자동배정에도 재사용.
3. **작업자별 AI 자동배정** — 2번에서 만든 LLM 연동 기반 위에서 진행. "추천" 단계로
   먼저 시작(워크로드 기반, LLM 없이도 가능)한 뒤 LLM 기반 적합도 판단을 얹는 2단계
   접근을 권장.
4. **구글시트 연동** — 위 셋과 기술적으로 독립적이라 병렬로 진행 가능. 다만 Google
   Cloud 콘솔 설정 등 코드 외 준비가 필요해 실제 착수 타이밍은 별도 조율 필요.

일정(몇 주/몇 개월)은 이 문서에서 다루지 않는다 — 실제 착수 시점에 리소스와 우선순위를
다시 논의해 결정한다.
